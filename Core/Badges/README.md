# Badges

The Naowh Forever badge next to the names of Naowh, the developers, the moderators, EllesmereUI's
creator and Legendary, Epic and Basic patrons: in chat, on a card when you hover the name, on a plate over their
player tooltip, after their name in the Guild & Communities list, and in a banner when one joins
your group. Each part has its own switch in QoL > Interface (`ns.FEATURES.qol.badgeChat`,
`badgeCard`, `badgeTooltip`, `badgeBanner`). Loads through `Badges.xml`, after the core, before
`Core/Pages.xml`.

## Layout

```
Core/Badges/
  Badges.xml                       the lists first, then the code that reads them
  Staff.lua     the team, edited by hand in a pull request (ns.BADGE_STAFF)
  Patrons.lua   the active Legendary, Epic and Basic patrons, generated by the daily badge sync
                                   (Tools/release/sync_badges.py); never edited by hand
  Confirm.lua         a patron's badge confirmed by their own client: the claim and BattleTag
                                   check, /nf badges claim, and the addon whispers that ask and answer
  Badges.lua          the tiers, the chat badge and its card, the tooltip plate, the list
                                   badge, the group banner, /nf badges, and ns.BadgeOf for other modules
  Media/                           each tier's badge art, a chat size and a large one (Badge<Tier>Chat.tga,
                                   Badge<Tier>Large.tga)
```

## Staff list

Keyed by region (`GetCurrentRegion`), then character GUID. A tier is "naowh", "developer",
"moderator" or "ellesmere", or a table with a personal title. `/nf badges id` gives the code to
add: "90:Player-4613-006EB819" goes under `[90]`. A staff entry wins over a patron one.

## Why

- Characters are keyed by GUID because Forever names (first name and surname) are not unique, and
  by region because regions have their own characters: another region's list is never read, so a
  GUID that exists in two regions cannot borrow a badge. Forever reports its own region numbers,
  not retail's 1 to 5.
- While `ns.FEATURE_BADGES` is 0 only the team's badges show, on the settings' defaults whatever a
  profile saved: no patron tier or list, no settings card, no words about support.
- Badges, card and tooltip start on so everyone sees them; the banner starts off (Naowh's call).
- A patron's tier comes from the list: `tier = "epic"` for an Epic patron, `tier = "basic"` for a Basic one,
  and Legendary when there is none (or one the addon doesn't know), so a list from before Epic still reads
  right. Epic wears epic purple, so the moderators moved to red. Basic wears rare blue, the next quality
  down, and its group banner plays the lesser loot toast.
- The chat badge goes after the name, so every name starts where it would without one. It is as
  tall as the chat text and sits one pixel lower (`BADGE_DROP`): the fonts leave room above their
  capitals. Blizzard skips the name filter when a name is secret, so restricted chat is untouched.
- Hovering a name finds its sender through a ring of reused slots (chat line to GUID), so no table
  is made per message; the card needs the chat badges for that.
- The tooltip plate is ours, anchored to the tooltip, never the other way round, and watched from
  the plate rather than by hooking GameTooltip's scripts: OnTooltipCleared runs inside the game's
  own tooltip building, and a hook there got the game's unit colouring reported as tainted by
  Naowh Forever. A tooltip post-call cannot be removed, so it is added the first time it is wanted
  and checks the setting itself.
- The Guild & Communities list reuses its rows as it scrolls; the badge is our own texture kept in
  a side table, read from Blizzard's field (never written), and hidden when the row is someone else.
- The group banner shows once per supporter per group. Logging in or reloading inside a group
  notes who is there without a banner; a scan put off by combat keeps that quiet unless someone
  joined mid-fight.
- Previews and test banners are staff only, so nobody can screenshot a badge they do not have.
- Every character you log into is remembered by region, one write per login, so `/nf badges id`
  gives one code for your main and your alts.
- naowh.gg cannot tell whose character a badge code is: anyone could add someone else's. So each
  character a patron adds gets a random claim (`K7P2-9XQM`) that reaches only the patron: the
  Naowh Forever app writes it into its own `NaowhForever_Claims` addon (`ns.BADGE_CLAIMS`), or
  they type `/nf badges claim` with it, kept in `badgeClaims`. The list carries `claim`, a 32-bit
  FNV-1a hash of "claim|BattleTag|GUID" with the BattleTag saved on their naowh.gg account (patrons
  with none are left out), and a patron badge shows to its own faction only once that character's
  client gets the same hash from its claim and its own `BNGetInfo()` BattleTag. A character added
  for someone else never gets its claim typed or written on that character, and a claim handed to
  a friend fails on the friend's BattleTag. The random claim in the hash keeps the BattleTag from
  being guessed from the public list. A patron whose claim does not match is told so, once.
- The confirmation is an addon whisper: seeing an unconfirmed patron (chat, tooltip, guild list,
  group) asks that character once a minute at most, ten asks per ten seconds, and only their
  client's yes within ten seconds counts. Answers are rate-limited the same way. The game vouches
  for who sent a whisper, so another character cannot answer for them. Nothing is sent while
  addon chat is locked down.
- The other faction cannot be whispered on Forever, so it sees patron badges as the list has
  them, unconfirmed. The team's badges are reviewed in a pull request and need no confirmation.
- A stranger's first chat line shows without the badge (lines cannot be changed once printed);
  the next one has it. The group banner waits for the yes.
- The Your Badge card sits at the top of Profiles, since your badge belongs to you rather than to a
  setting: it says whether this character's badge is confirmed, still checking, not claimed yet,
  or off because the claim or BattleTag does not match. `/nf badges status` prints the same line for support questions.
- Patron confirmation listens only while patron badges are live and the list has a patron, so with
  `ns.FEATURE_BADGES` at 0 nothing is registered.
