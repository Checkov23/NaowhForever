# Core

The namespace every other file builds on (`_G.NaowhForever`), the theme and the house chrome, the
saved settings and their profiles, the feature switches, the options window with its pages, the
HUD Editor (Unlock Mode), the profile strings, the QoL settings store, and the
first-run windows. It loads at five points of the core TOC, each through its own XML: `Core.xml`
first, `Options.xml` after the RestedXP themes, `Profiles.xml` and `Settings.xml` after Shared, and
`Pages.xml` last, after the Badges.

Shared internal tables between split files: `ns.HudEditor` (the HUD Editor files), `ns.Options`
(Modules, Window, SettingsPage, Commands, Launchers) and `ns.Profiles` (ProfileShare and its
dialogs and page). They are not an API for modules.

## Feature switches

`ns.FEATURES` holds every switch's default, grouped by the settings store that keeps it:
`ns.FEATURES.qol.bagSpace` is QoL's `bagSpace`, `ns.FEATURES.account.rxpThemes` is the account
setting. A settings store reads its on/off defaults from there (`UI.ModuleSettings("journal",
{ enabled = F.journal.enabled, ... })`), and an account switch reads its default there when the
saved value is nil. The tables are strict: an unknown store or key raises an error, so a typo
fails at load instead of reading as off. `Tools/regression/test-features.lua` checks that every
switch a settings store declares is in the file, and that every account switch is read through it.

`ns.FEATURE_BADGES` is a build flag, not a setting: 0 shows only the team's badges, with no patron
tier, no settings card and no words about support (Credits and Patch Notes leave those lines out).
At 1, `Badges.lua` adds Naowh's Patreon to the link icons (`ns.LINKS`), after the others.

## Why

The QoL store and the Alerts group
- The QoL store is in the core, not in the optional QoL addon: its defaults hold the preset, the BiS,
  Gear Sets, Blessings and Group Inspect switches, the character and inspect panels, the badges
  and keys the setup reads. It loads where QoL's own files used to, before the Badges.
- The Alerts group (Camp Nearby, Talent Points, Durability, Restock, Pet Tracker) is the bottom
  slot; its mover covers the whole stack, so anchors measure what the player sees. Order 1 is the
  bottom. Its members belong to QoL and Aura Buffs, so it lives here and the mover plate follows
  whichever previews are up. Every alert previews in the HUD Editor, so its Settings asks which
  alert to open rather than guessing from what is showing.
- Before the group each alert had its own spot (`OLD_POSITIONS`): the first one a player had
  moved, from the bottom up, becomes the group's.
- A key binding whose module is off prints that it is switched off (`SwitchedOff`), instead of
  calling a function that was never made. The bindings for the modules' own windows and settings
  (`NaowhForever_ToggleModule`) go through `OpenModule`, which says the same.

Namespace and builds
- `MODULE_KEY` must match the addon folder: the DB and saved positions key off it.
- `ns.MEDIA` is the core's art folder, written once in `Core.lua`; the core's files and the
  modules read it. `ns.BADGES_LIVE` (1) is the value `ns.FEATURE_BADGES` takes once supporter
  badges launch, read by every file that checks the flag.
- `UI.PROFILES_PAGE` is the Profiles page's key, set where the system pages are listed
  (`Options/Modules.lua`) and read by the window's sidebar and the Profiles page itself. That
  page's head, group rows and two-column width come from `Shared.Settings.Style`, so it lines
  up with a settings page.
- `ns.CODE_BUILD` is bumped by hand on every build sent to a tester and printed beside the TOC
  version, which only moves on release. A report naming a stamp the reporter was not sent comes
  from a client that was not reloaded.
- Libs/ is not in git; the packager adds it. An install from the source zip has none, so login
  says so once instead of features failing one by one.
- The Damage Meter module is no longer shipped (its folder stays in git). It turned the game's meter
  (`damageMeterEnabled`) off and kept what it was on the account, so the core puts that back at login
  when the addon is not loaded.
- QoL's Glimmer changes soft target and outline settings and keeps what they were on the account; the
  core puts those back at login too when NaowhForever_QoL is not loaded, so turning QoL off in the
  AddOns list, or applying a preset that turns it off, never leaves them changed.

Theme
- Naowh's scheme is dark grey with his blue (#0091ed) as the single accent. Each preset keeps text
  at 4.5:1 and secondary text and accent at 3:1 against its own background and panel (a test
  checks it).
- Player colors are written into `ns.THEME`'s tables in place, once per load and before any window
  is built, so every file's `local T = ns.THEME` sees them; a new pick takes a reload. Read
  `ns.Color` and `ns.ThemeTint` when a frame is built, never at file load.
- The lighter accent and the selection fill follow the accent and the line. A pick equal to the
  shipped color is not a change: Custom starts as a copy, and the color picker hands back what it
  opened with.
- The Forever skin (Settings > Skin) has its own colors, `ns.FOREVER_SKIN`, in force whatever the
  Theme setting says: parchment text on charcoal stone, bronze lines and the game's gold. It is read
  with the colors, once per load, so a change to it waits for a reload too. `ns.Skin()` says which
  skin is in force; a saved skin it does not know is Naowh's. The Theme dropdown is greyed out under it.
- The Classic+ skin is gone: a saved `skin = "classic"` is saved as `"forever"` when the colors are
  read, so a Classic+ player gets the other game skin rather than Naowh's.
- A secret-tainted message is dropped silently by the chat display, and `tostring` on a secret
  returns a secret string, so `ns.Print` asks `issecretvalue` before coercing anything.

Fonts and pixels
- The Naowh font is bundled so it works without NaowhUI_Media, and registered under the same name
  and locale mask; when NaowhUI_Media is installed its entry wins (LibSharedMedia never overwrites)
  and its Asia variant covers CJK clients.
- The Naowh font starts a straight-sided capital 75/1000 of its size in (`STEM_INSET`), so lines of
  different sizes set at one x look ragged; `ns.FontInset` moves each line left by its inset.
- Unpicked, the Addon Font is Naowh, or the game's Arial Narrow on Forever. Headings (`ns.Font`'s
  `heading`: buttons, tabs, titles, card and section names) are the game's Friz Quadrata on
  Forever unless an Addon Font is picked.
- Game Font and Combat Text Font touch only font objects and the three path globals, never a frame:
  taint-free, but with no undo, so a change takes a reload. The path globals are read when the
  world loads, so they are set on ADDON_LOADED and again at login; combat text inherits
  SystemFont_World, which Game Font changes, so it is set after.
- At most UI scales one unit is less than a screen pixel and the client snaps edges, so a one-unit
  line vanishes on some sides. `ns.Hairline`, `ns.PixelInset` and `ns.Border` work in screen pixels
  from the region's own scale, again whenever its frame shows or the scale changes. The owner is
  watched through a child frame: a module calling SetScript("OnShow") later would drop a hook.

Reload UI
- The game blocks an addon's own reload, even from a click, but runs /reload from a secure macro
  button. A protected frame inside our windows would lock them in combat, so one button lives on
  UIParent, laid over the hovered Reload UI button by screen position (never anchored), and hides
  as combat starts.

Modals and windows
- One modal shell per key, reused on every open: frames are never freed, so new frames per open
  leaked every earlier copy. Opening a key that is up closes it first.
- Modal levels come from a private counter, not `Raise()` (unbounded across UIParent), and wind
  back past 150 so the panel stays under 200, the hardcoded dropdown level.
- Escape is our own keyboard handler, not UISpecialFrames: a named addon frame in that table taints
  CloseAllWindows. `SetPropagateKeyboardInput` is protected, so in combat the keyboard is not taken
  at all (taking it without propagation swallows every keybind); the close button still works.
- The full-screen dimmer keeps the mouse off so what is underneath stays clickable.
- The game menu button goes in through `MainMenuFrameMixin.AddButton`, not the menu's own
  `AddButton`, which also lists it in `GameMenuFrame.buttons`. In gamepad mode the menu's OnHide
  walks that list and then calls the protected `SetGamePadCursorControl`, so our entry got every
  close, Options included, forbidden. Our own click hides the menu from addon code and would hit
  the same call, so the button is left out while `ns.GamepadOwnsPanels()`; /nf still opens the window.
  The input style follows the last device used, so the menu can switch to gamepad while it is open:
  the click checks again and then leaves the menu open under the window.
- `ns.GamepadOwnsPanels()` is true while Blizzard's gamepad handling runs when its panels open or
  close: the gamepad UI (footer override bindings, blocked in combat) or gamepad cursor auto-control
  (`ShowUIPanel`, the game menu and bags call the protected `SetGamePadCursorControl`). Opening or
  closing a Blizzard panel from addon code then gets forbidden, so anything that would (the game
  menu button, the Top Bar clock, custom slash commands) stands down.
- The options window is DIALOG and the HUD Editor draws at HIGH, so the two never share the
  screen: Unlock Mode steps the window out and puts it back on exit. Stash the window before
  arming, or its OnHide disarms the mode in the same click.
- The window rebuilds at most once a frame, and while hidden waits for the next open, so page
  builds (previews, lazy journal reads) never run off-screen. A profile import can change any tab, so
  every cached tab is invalidated, not only the one on show.
- Window scale is set from a dropdown, not a slider: the control sits inside the frame it resizes.
- Sidebar rows are 28 high (`NAV_ROW`) so every module fits the default 852-high window
  (test-navigation.lua).
- The options window and a module's window size through `Parts.Resizable`; letting go of the grip
  (`onReleased`) fits the page to the new width and redraws it only when that width changed.

Settings and profiles
- Profiles are account-wide with a per-character active pointer (name-realm). Forever returns
  "Unknown" for the player's name early in loading; anything read then got the account default and
  is reapplied once the name is known.
- Account settings sit outside the profiles: the window scale follows the monitor, so a profile
  switch leaves it alone.
- The UI scale is clamped on read as well as write: a zero scale hides the window with no way back.
- Switching profile on a spec change is off unless asked for: unasked it reads as a bug. A manual
  switch teaches the spec map, so auto switching does not undo it. A map entry for a deleted
  profile is ignored rather than recreating it.
- An account-wide import turns auto switching off (keeping the map): otherwise every alt went
  straight back to its old profile.
- A deleted "Default" is replaced as the account default, or a later first login starts empty.
- Reapplies are coalesced: two switches in one frame apply once.
- The TTS voice list is cached because `GetTtsVoices` builds a table per call. Blizzard's TTS panel
  raises no event, so closing it or Settings drops the cache (not combat start, which stalled
  every pull). An empty list early in a session is never cached.

Widgets
- A tooltip is sized after it shows: a hidden frame's text reports the wrong size. In restricted
  content a string's size can be secret, so it is checked first.
- The pill switch is antialiased art (`toggle_track.tga`, 128x64 for the 2:1 ratio) tinted with
  SetVertexColor; WoW has no rounded rectangle and a mask gets about one pixel of gradient.
  Pixel snapping is turned off on it, as Blizzard's NineSlice does.
- Dropdowns open with `OpenMenu` anchored to the button and answer `HandlesGlobalMouseEvent`, or
  the menu manager's GLOBAL_MOUSE_DOWN close made OnClick reopen it. Scrolling is opt-in on
  Blizzard's menu; unset, a long list ran off the screen.
- A slider drag ends when the button comes up anywhere; while it runs `UI.sliderDrag` is set so a
  page that redraws on change waits for the release.
- `UI.Keep` hands back what a call site made last build, in build order, on pages that reuse rows.
  Config tables stay attached to their controls and are updated in place, so never share one config
  table between two rows.
- The color picker saves nothing until the color moves off the one it opened with.
- A row region's `onDrop` takes whatever the cursor holds: a drag let go anywhere on the region,
  its button included, or a click while the cursor holds something. It returns true when it took
  it; a button whose `onDrop` did not then runs its own click.
- `ns.NewEditBox(parent, opts)` is every input box. `opts` is optional: `inset` (the text inset),
  `border` (its edge color, black by default), `hover = false` (no accent edge under the mouse) and
  `sunken = false` (no Forever rim). A settings row's text box is one with no hover.
- The Slider's own thumb drag runs against the cursor on Forever, so the slim scroll bar's grip
  takes the mouse and drags itself.
- Sound and font choice tables are fresh per call: the SharedMedia appender mutates in place and
  caches by table identity. The sound path cache is dropped when SharedMedia registers more (boss
  mods do after login); a missing optional provider is not a cached miss.
- Every module's defaults are saved to the account at login, so a module whose addon is off still
  has its settings checked, exported and imported.
- On Forever a field has a bronze rim one pixel outside its black edge (`Parts.ForeverField`), and
  a button is the game's red `128-RedButton` (`Parts.ForeverButton`, see Shared/README.md); its
  pieces are its `_art`, and drawn, its bronze rim hangs off the edge's frame, so the
  Flight Timer fades them with the rest. `ns.AccentBorder` leaves the game's button art alone: the
  game marks no button as the main one.
- `UI.KeyField` takes a binding command, or functions for its action and label, for one field
  pointed at another binding each time its panel opens; its `_refreshValue` shows the new one.

HUD Editor
- An element is placed CENTER on the screen centre in whole pixels. An anchor keeps, along the
  target's side, a centre-to-centre offset and, across it, the gap between the facing edges, so a
  target that grows pushes the element out. The offset along the side is taken from the target's
  frame, not its plate: the Alerts plate grows from the bottom with every alert and with the HUD
  Editor's previews, and an element off its side followed it up and down. Anchors are reapplied
  parents first, after entering the world, every profile switch and combat (a protected element
  waits for combat to end).
- Installs before 1.1.3 shipped the Loot Feed anchored to Alerts by accident, and players who
  moved it kept an anchor to Alerts, some on its top side where the growing plate still carried
  the feed. Each profile lets go of any Loot Feed anchor to Alerts once, in its saved layouts too
  (`lootFeedOffAlerts`); the feed stays at its own saved spot.
- An element that grows one way (`UI.SetMoverGrow`, the Blessing Bar) keeps that edge on its
  anchor instead of its centre, along the target's side, so it widens away from where it was put.
  Changing the way it grows takes the offset again from where it is, so it does not move.
  `UI.SetAnchor` anchors an element from its own settings (Reset Position), `UI.HasAnchor` asks.
- Size and position changes are queued and handled once a frame.
- Before each change by hand the editor keeps every element's spot and anchor (50 steps); a run of
  arrow nudges to one selection is one step. Loading a layout is a change like any other.
- A module's resize grip sizes from its own corner, so the anchor leaves the frame alone until
  the grip lets go.
- On the Forever skin the toolbar, the Elements list and the movers wear Blizzard's Edit Mode look
  (its selection art, the metal frame, a Layouts dropdown): `Shared/README.md`, The HUD Editor on
  Forever, names each atlas and the file it comes from.
- The main chunk of a Lua 5.1 file holds at most 200 locals, which is why the HUD Editor, the
  window and the setup window group their sizes into tables.

Profile strings
- Forever's Lua raises on 1 / 0, which LibSerialize does to every 0 it writes (to spot -0), so a
  profile string sends 0 as a marker and puts it back on import.
- Reminder Packs (`NSRPACK2:`) are gone. An old pack string is refused before anything in it is
  read, in the Import box and through `NaowhForever_API:ImportProfile`, with a message saying so.
- The Share picker offers Settings, Macros, Talent Builds, BiS Lists, Saved Quest Items and Look.
  Macro Library and Consumables are no longer exported, but a string from an older build that carries
  them still lists them on Import, and `NaowhForever_API:ImportProfile` still takes them. The
  Consumables part is only `utilityReminders.consumables` from the reminders' store, and its import
  replaces only that list. The store keeps its saved key, `tankReminder`: renaming saved data would
  need a migration.
- Saved Quest Items is `qol.questRewards`, the Alt-click reward picks, as a part of its own and
  left out of the Settings part (`ns.PROFILE_OWN`), so unticking it keeps them out of the string.
  Like every part it starts ticked. Import replaces the new profile's picks with the string's. A
  string from before the part existed carries them inside Settings; the decode lifts them out into
  the part, and a `questRewards` part wins over them. The part is checked whole (quest and item
  IDs whole numbers from 1 to 2^31 - 1, at most 2000 picks), and one bad pick leaves it all out.
- A string from an older build has its consumables inside a `smartReminders` or `reminders` part;
  the decode takes only those from either, and a `consumables` part wins over both. Older builds
  ignore the `consumables` key, so a string from this build brings them no consumables.
- Class macros travel only in the Macros part, never with the consumables.
- Consumables and class macros come from another player, so each list is checked whole: IDs are
  whole numbers from 1 to 2^31 - 1, categories and class tokens are known shapes, names, bodies
  and notes fit the game's limits, lists have no holes, and there are at most 500 consumables and
  100 class macros a class. One bad entry leaves that whole part out, and only the fields the addon
  reads are copied in.
- What one player answered about EllesmereUI's windows, and their invite buttons' friends (`ns.PROFILE_OWN`),
  are never shared.
- A module's on/off is its switch in the profile (`enabled`, or the QoL key the module reads) and, for
  this character, its addon in the WoW AddOn list. The Settings part also carries each module's addon
  name and state (`__modules`, read from this character's list); import writes it as the new profile's
  switches, and the AddOn list follows when that profile is switched to (see Module state).
- The skin travels in a profile string's Look part, with the theme, font and window scale. A
  consumable needs only its item ID; its buff IDs may be left out.
- A multiline edit box is as tall as its text, so an empty one is given a height or it takes no
  clicks; a bare EditBox has no click-to-focus. The import dialog is cached, so the parts ticked
  for one string are cleared each time it opens.
- Keep My Positions, a row of the Import dialog that starts ticked, keeps where your HUD sits: each
  module saves its own position under its own key (`alertsPos`, `pos`, `meterPos2`...), with no
  shared naming, so `Positions.lua` lists them by store, with the bars pinned to a unit frame
  (`<bar>Anchor`, `X`, `Y`), the sizes you drag (Damage and Threat Meter, Loot Feed) and the HUD
  Editor's attachments, hidden and locked elements and layouts. They are read from the profile you
  are on before the import and written over the new one after it, copied, and a frame you never
  moved is cleared so it takes its default rather than the string's. Window positions are saved for
  the account and an import never touches them. A new mover's key goes on the list;
  `test-position-keys` fails on a saved `...Pos` key that is missing. `NaowhForever_API:ImportProfile`
  never keeps them: the installer lands a whole layout on purpose.
- The Setups card's Keep My Positions does the same when a setup is applied from the card. It is
  saved for the account (`presetKeepPositions`, on unless set false), since applying a setup
  replaces the profile's QoL settings and a profile string would carry it. The onboarding applies its setup without it, so a new install still gets
  the team's HUD.
- `NaowhForever_API:ImportProfile(str, "Naowh")` is the NaowhUI installer's entry point: it lands
  the string as that profile, replacing it, and moves every character to it. It prints its own
  failures because the installer ignores return values.
- WagoUI Packs drives the same global table: `ExportProfile(key)` (any profile by name, the same
  string the Profiles page makes with every part ticked), `ImportProfile(str, key)`,
  `DecodeProfileString(str)` (the string's parts, for comparing), `SetProfile(key)` (this
  character only), `GetProfileKeys()`, `GetProfileAssignments()`, `GetCurrentProfileKey()`,
  `OpenConfig()` and `CloseConfig()`. Profile key = profile name. None of them reload the UI
  themselves, but switching to a profile whose module switches differ from this character's
  AddOn list changes the list and brings up the reload prompt (see Module state).
- The AddOn list belongs to the character, not the profile, so a profile that is not the current one
  exports its modules (`__modules`) from its own switches, leaving out a module whose addon is not
  loaded here, and an export never writes to the profile it reads.

Waypoints
- Guide waypoints carry optional quest/objective context through the same map-open hold as other placements. `GuideWaypointIsCurrent` checks coordinates before a guide clears anything, so a manual replacement is preserved.
- The game redraws the world map's waypoint pin inside every change to its waypoint, so while that
  map is open a change waits for it to close: made from addon code it would taint the pin and the
  game would block its Share.
- Only the last TomTom waypoint is kept, so clicking pin after pin does not pile up arrows. Routes
  always use the game's waypoint, since TomTom's never reports arriving.
- `ns.PlaceWaypoint`'s last argument, for a dungeon's entrance, clears the waypoint as you go from
  outside a dungeon or raid to inside one, so it is done wherever you walked in. Every game
  waypoint placed since, a Journeys step included, drops it, and a waypoint set since by hand is
  left alone. A Journeys route or TomTom's arrow does not carry it.

Senders
- Forever names are a first name and a surname and are not unique, so a message's sender is
  matched to a GUID through your group, guild or friends; anything that cannot be matched is
  dropped.

Search
- The sidebar search offers seven reusable result rows with module/section paths. Up/Down and
  Enter navigate the results; selecting one clears the filter, reveals the setting and briefly
  highlights its row. Carried settings pages use the host page's view for the same jump.
- Pending reload changes mark every Reload UI button with an asterisk and keep the reason in
  its tooltip, even after the confirmation is dismissed. The mark lasts until the UI reloads.
- `ns.PrimaryButton(button)` applies the Naowh accent fill; the HUD Editor uses this treatment.
- Every typed word has to start a word of the target, or be close to a word of its name: its
  letters in order (a Lua pattern, `^()t.-()o.-`) in a word that starts with the same letter and is
  at most twice as long, from three letters typed. Help is matched only by word starts: matched
  closely it found something in almost every help text. Close matches come after every exact one,
  the ones whose word was most fully typed first. A pattern holds at most 32 captures, so a longer
  typed word is only matched exactly.
- A module with one tab does not add its tab's name (mostly "Settings", which would match "set"
  everywhere).
- A setting's module and tab names can narrow it ("journal minimap") but never find it alone, or
  typing a module's name would count every setting it has.
- A page its own builder draws (Settings, Profiles) names what is on it through `terms`; the
  Settings page runs its own sections into a recorder, so what is searched is what is drawn.
- A module that is not loaded declares no pages, so it is searched from the generated index in the
  load-on-demand `NaowhForever_SearchIndex` addon (built at release), loaded by the first search while a module is off.
  Its matches put it in a Turned Off group at the bottom of the sidebar, shown only while the search
  finds something in it; its page lists them and its header switch turns it on. Its name is also
  found on the Settings page, which says it is off.
- A window card is searched by its button and its fixed text, never by a headline function: those
  read live state and some do real work.

Onboarding
- The onboarding opens once per account, a few seconds into the first login and out of combat;
  nothing is made until then. Closing it any way marks it seen (`onboardingSeen`); hiding the whole
  UI is not a close. It has its own flag so players who saw the old welcome window get it once too.
- Closing it also sets `welcomeSeen`, which the Character Panel reads to tell a player new to the
  addon from anyone else; players who saw the old welcome window already have it, so they are not
  treated as new.
- The onboarding asks three things, a step each: a profile (Naowh's Minimalist or Everything Enabled, or
  Keep mine), a skin, and the modules; then a summary of what changes, and Apply. Players new to addons
  do not want many choices, so it no longer asks about how they play.
- The profile step starts on Minimalist, the preset a new install starts from (`newInstall`), only for
  an account never set up: no `welcomeSeen` (the onboarding or the old welcome never closed) and no
  `setupBefore` (no Apply yet). Anyone else starts on Keep mine, so opening it again changes nothing unless they pick something.
- The modules step starts from the picked profile: when a preset has a `modulesOff` list, every
  module but those (Minimalist keeps only Quality of Life, the Dungeon Journal and the BiS List, for
  players who would rather opt in; Everything Enabled's list is empty, so every module is on), else its
  switches, with the feature's default for a switch it leaves out; Keep mine starts from what is on
  now (its addon enabled, for this character in its own mode, and its switch on). A module on without
  what it needs (`needs` in `Options/Modules.lua`) cannot run, so it starts off. Picking another
  profile starts the modules again; going back and forth keeps the flips. A flip on brings what it
  needs, a flip off takes what needs it (`ns.LinkedAddons`).
- A preset's `modulesOff` is defined once, in `Tools/build/presets.lua`'s INFO. The build writes it
  into Presets.lua and as the switches in the preset's profile, so a new install starting from it
  agrees; `ns.ApplyPreset` writes it as the modules' switches (`Setup.PresetSwitches`), so applying
  Minimalist from the Setups card and from the onboarding agree. A module listed nowhere is on.
- The Setups card also enables the addon of every module the preset turns on and, through
  `ns.ReconcileModules`, disables the addon of every module it turns off; its hover counts a module
  whose addon is not loaded.
- Apply backs up first (`setupBefore`: the profile, each module addon's state, whose it was and the
  skin), applies the profile as the Setups card does (`ns.ApplyPreset`, without its confirms), sets the
  skin, then each module: on enables its addon and switches it on (through its store when loaded, so
  it starts at once); off disables its addon if it is on, or, after a preset, if it is enabled at all,
  and writes its switch off, so Minimalist leaves exactly its list. Keep mine leaves an enabled module that is switched off as
  it is.
- A reload is asked only when something needs one: a profile or a skin applied, a module turned on
  whose addon is not loaded, or a loaded one turned off; else the done line is printed. The summary
  works this out the same way (`Setup.Plan`), and Apply with nothing to change just closes.
- Apply marks the setup `custom` when its modules differ from the picked profile's (or, for Keep
  mine, from what was on), and sets `characterPanelPicked` and `inspectPanelPicked` when the BiS List
  stays on with that panel on, so after the reload Naowh's panel takes over from EllesmereUI's without
  asking (`NaowhForever_BiS/CharacterPanel`).
- Restore puts back the profile, the module addons for the character the backup was made for, and
  the skin; a backup from before skins were saved leaves the skin alone.
- The skin step's previews are drawn, not pictures: a small window in each skin's own colors
  (`ns.ThemePalette` for Naowh's, with the player's theme; `ns.FOREVER_SKIN`), edge,
  fonts (`ns.AddonFontPath` and `ns.HeadingFontPath` take whether to preview the game's) and button.
  Forever's is a small Forever window built from the skin's own parts whichever skin is on: the rock
  backdrop in Forever's palette (`Parts.Backdrop(frame, true)`, `Paint(1, ns.FOREVER_SKIN)`), the
  portrait frame with its gold title and red close (`Parts.ForeverFrame` with `preview`, so it
  neither drags nor closes) and the game's red button (`Parts.ForeverButtonArt`). The game's frame art
  cannot be sized down, so the little window is a frame at `FOREVER_PREVIEW.scale` of real size, its
  text and button sized up by the same amount to match the Naowh preview's on screen. It is inset in
  the preview's box by the room the frame's art takes outside the window: `FOREVER_SIDE` plus the
  portrait corner's 13 to the left, `FOREVER_TITLE_H` plus its 16 above (`PortraitFrameTemplate` in
  `NineSliceLayouts.lua`), and `FOREVER_SIDE` plus the drawn rim's 5 to the right and below. The text
  starts under the header band (`WINDOW_HEADER`), clear of the portrait, as in a real window.
  The step has a tile per skin in `Setup.SKINS` (Naowh, Forever), side by side.
- The modules step lists the modules that are on first and the ones off under a line, each group in
  the options' order; a flip moves its tile across at once, laid out again from the same tiles. Four
  tiles a row keep up to 21 modules above the footer, with both groups shown.
- A character new to the account gets its own page in the onboarding window, after the onboarding has
  been seen: two tiles, Same as its main or Set Up on its own, with the welcome's bottom row and no
  Back or Next. A new character starts on the account's profile, usually the main's, so the main no
  longer has to be on a different profile.
- The main is the first character made on this character's server. Every login saves the character's
  GUID (`charGuid`); a player GUID is `Player-<server>-<counter>`, and the counter is handed out per
  realm and grows with each character made, so the lowest counter on the same server is the oldest.
  Nothing else records creation order (`charSeen` is the last login, /played is not kept per
  character). With no other GUID known on the server, it falls back to the character played most
  recently, then the one whose profile most other characters use, then by name. A provisional
  `Unknown-` key (written before the game knew the name) is never offered. Deleted characters stay in
  the saved lists: addons cannot see the account's character list.
- The page waits for an answer across reloads and relogs: a new character is saved in the account's
  `charAsk` (by name-realm, as `charActive` and `charSeen`). `ns.MarkAsked` clears it when the page is
  answered, when the window is closed (X or Escape), or when the full onboarding is closed on that
  character; hiding the whole UI is not a close. A character first seen before the account saw the
  onboarding gets the onboarding instead, and closing it answers the page too.
- Same as switches only when the main's profile is not already this character's, and says so; either
  way the window closes. Set Up copies the character's current profile into one named after it
  (" 2", " 3" when taken), switches only this character to it and goes on to the profile step in
  the same window, for this character alone; the profile picked there is applied to that new profile. `ns.CreateProfile` is not used: it switches every
  character. A copy that fails changes nothing and the page stays.
- The page is laid out as the welcome: its animated infinity sign near the top (spinning only while
  the page shows), then the head and muted body at the welcome's sizes and gaps, then the steps'
  own tiles (`Tile`, `LayoutTile`, `PaintTile`) with Core/Media's chain and wand as their icons.
- For one character, the onboarding turns module addons on and off with `UnitGUID("player")` passed to
  `C_AddOns.EnableAddOn`, `DisableAddOn` and `GetAddOnEnableState`, as Blizzard's AddOn List does; with
  no character they mean every character. The backup keeps the GUID, so Restore puts back that
  character's addons.
- `ns.ModuleAddons(who)` reads the all-characters state, or with a GUID that character's, so in one
  character's mode a module enabled only on other characters reads as off, and every C_AddOns call
  names it.

Module state
- Every module is its own addon, so the AddOn list decides what loads, per character, and a disabled
  addon cannot report anything. The core keeps the answer in the profile: each module's switch
  (`Setup.ITEMS` names it: `db` and `key`), written explicitly when a module is turned on or off from
  Settings, a module's window, the onboarding or an import. `ns.SetModuleState(addon, on)` writes the
  switch and this character's list (`UnitGUID("player")`, never every character) together.
- `ns.ReconcileModules` makes the list match the profile. It runs 8 seconds after login, when a profile
  is switched to (`ns.SwitchProfile`, so a spec swap to a profile with other switches too,
  `ns.SetAccountProfile`) and after a Setups card apply, and costs
  one pass over the modules; no events or timers are kept. It does nothing before `onboardingSeen`, so
  a first install follows the onboarding.
- Each character keeps what its list was at the last pass (`account.moduleList`, by GUID). A list
  changed since (the game's AddOn list) is adopted into the profile; otherwise an explicit switch in
  the profile is applied to the list (another character's change, an import, a new character on the
  account's profile); a module with no switch follows the list. With nothing kept yet (a character
  that predates this, or a new one) off wins: a module off in either place ends off in both, so an
  addon turned off in the old way is not turned back on, and a new character does not bring back
  what was turned off. A module whose switch is only its default is not written to.
- A module on without what it needs is turned off (`Setup.Settle`), and turning a module on or off
  from Settings brings or takes the linked ones (`ns.LinkedAddons`), as before.
- The Top Bar is part of QoL, with no item and no AddOn list entry of its own: its switch is its card's.
- A module with a `host` (the seven in NaowhForever_Combat, the five in NaowhForever_Utilities) has no
  AddOn list entry of its own: it is on when its host is enabled and its switch is on.
  `ns.SetModuleState`, `ns.ReconcileModules` and the onboarding's Apply keep the host enabled for this
  character while any of its modules is on and disable it once none is; switching one while its host
  is loaded needs no reload, and switching one on switches on what it `needs`. A module counts as loaded
  only while what it `needs` is loaded too, since a host does not depend on it (Group Inspect in
  Utilities, needing the BiS List): until then Settings > Modules reads it from the AddOn list with
  what it needs (`ns.ModuleListed`), turning it on asks for the reload, and the onboarding plans one.
  Turning a hosted module off only sets its switch while its host is loaded.
- `ns.ModuleOn(addon)` says whether a module is on for this character: loaded, listed and switched on.
  A module reading another one that may ship in a combined addon asks it, not whether that one's
  functions exist, since a hosted module's files stay loaded while its switch is off.
- A change to the list takes a reload: one prompt (`ns.ConfirmReload`) after a pass that changed
  something, held until combat ends. Settings > Modules and the module windows read this character's
  list together with the switch, so they agree with the game's AddOn list.

Credits
- Every Credits card keeps an emblem-wide slot for its art, a badge emblem or a smaller icon, so
  names and lines start at one x (`TEXT_LEFT`) on every card.
